## 1. What was built, and why

This is a teaching deployment for the class **"Building Agentic AI with Amazon Bedrock AgentCore"**. It has two separate applications:

| App | URL | Purpose |
|---|---|---|
| **TrialScout** | https://www.awsteach.com | A clinical-trial operations copilot. A Strands agent on AgentCore Runtime answers questions about a (synthetic) study portfolio, site performance, enrollment forecasts and SOP/protocol compliance. It uses two MCP servers through AgentCore Gateway and remembers users with AgentCore Memory. |
| **TrialScout Insights** | https://insights.awsteach.com | This app. A read-only teaching portal that shows how TrialScout (and Insights itself) is designed, deployed and running: architecture, live inventory, logs, metrics, LLM prompts and reasoning, source code, and a chatbot grounded in this file. TrialScout's header and sign-in page link here. |

Both apps use the same Cognito user pool, and each has its own app client. **Students create their own accounts** on either
sign-in page (username + password of 6 or more characters; no e-mail, no MFA). They pick a role at creation, either `analyst` or
`reader`, and the role cannot be changed afterwards. To try the other role, create a second account. One account works in both
apps. There are no shared demo accounts.
Every resource is tagged `Project=TrialScout, Owner=instructor, Environment=demo`. One command tears everything down
(`make teardown` / `make teardown-all`).

## 2. Where the data comes from

* **All TrialScout business data is synthetic.** `data/generate.py` generates it deterministically (fixed seed `20261026`; re-running gives byte-identical output). The sponsor ("Synthetica Bio"), the programs (TSX-1xx), the sites, SOPs and protocols are all fictional. There is **no patient-level data**; sites carry only aggregate, made-up metrics.
* **What is generated:** 25 studies with 12 months of enrollment history, 60 sites (each attached to one study), 8 SOP documents, 5 protocol excerpts (each with v1 and an amendment v2), and 8 machine-readable compliance rules extracted from the SOPs.
* **Where it is stored:**
  * Studies and sites: DynamoDB tables `trialscout-studies` and `trialscout-sites` (items `{pk, doc}`, encrypted with the KMS CMK, PITR on).
  * SOP and protocol markdown, `rules.json`, `protocols.json` and the retrieval index: the S3 bucket `trialscout-docs-<account>` (CMK).
* **Retrieval index:** `data/build_index.py` splits the 13 documents into 34 chunks at each `## ` heading and embeds every chunk with **Amazon Titan Text Embeddings v2** (512 dimensions, normalized). It writes `index/index.json`. `search_documents` ranks results with a hybrid score of 0.7 × cosine + 0.3 × keyword overlap, and falls back to keyword-only if Bedrock embeddings are unavailable.
* **Seeding:** `scripts/seed.py` (called by `make deploy` / `make seed`) generates the data, embeds it, and loads DynamoDB and S3. The MCP servers cache what they read for 5 minutes per microVM.
* **Insights data:** Insights has no business data of its own. It reads CloudFormation (inventory), CloudWatch Logs, CloudWatch metrics, the Bedrock model invocation log, this file, and a snapshot of the source code that the publish script uploads to its knowledge bucket.

## 3. Models (LLMs) in use

| Use | Model | Settings | Where |
|---|---|---|---|
| TrialScout agent reasoning and tool use | **Anthropic Claude Sonnet 4.6** on Amazon Bedrock, through the US cross-region inference profile `us.anthropic.claude-sonnet-4-6` | Converse streaming through Strands `BedrockModel`. **Adaptive thinking** (`thinking: {type: "adaptive"}`): Claude decides per step whether to reason first. max_tokens 8000, default temperature (thinking requires it). Guardrail attached (latest user message, sync stream processing). `requestMetadata {app, correlation_id, role}`. | `services/agent/main.py` |
| Insights chatbot | Same model, `us.anthropic.claude-sonnet-4-6` | Bedrock **ConverseStream** from Node.js. Adaptive thinking, with the reasoning streamed to the UI. max_tokens 16000. **Prompt caching:** a `cachePoint` after tools + system prompt + this knowledge file. Up to 8 tool rounds. `requestMetadata {app: insights-chatbot, correlation_id, round}`. | `lambdas/insights/chat.mjs` |
| Retrieval embeddings | **Amazon Titan Text Embeddings v2** (`amazon.titan-embed-text-v2:0`) | 512 dimensions, normalized. Used at seed time and per query in the Policy MCP server. | `data/build_index.py`, `services/mcp_policy/main.py` |
| Long-term memory extraction | Model managed by **AgentCore Memory**, run by the service | The user-preference strategy extracts durable preferences from conversation events, asynchronously (about 15–60 s). | `CfnMemory` in `infra/lib/agentcore-stack.ts` |
| Safety | **Amazon Bedrock Guardrails** `trialscout-guardrail` (not an LLM you prompt) | Prompt attack MEDIUM (input). Denied topics IndividualMedicalAdvice and TreatmentUnblinding. PII: email/phone anonymized, SSN blocked, names anonymized on input, MRN regex. | `infra/lib/foundation-stack.ts` |

**Why Sonnet 4.6?** In this account, Claude 5.x model IDs return `AccessDenied`. Sonnet 4.6 is the newest Claude model it can
invoke, and it supports adaptive thinking, interleaved thinking during tool use, and prompt caching on Bedrock. To switch
models, change `MODEL_ID` in `infra/lib/config.ts`.

## 4. TrialScout architecture (request path)

1. The browser loads a static SPA from S3 through **CloudFront**, which has AWS WAF, TLS 1.2+, HSTS and a strict CSP.
2. The user signs in with the in-page form (Cognito `InitiateAuth` USER_PASSWORD_AUTH over TLS) or the **Cognito hosted UI** (Authorization Code + PKCE). The Cognito group `analyst` or `reader` sets the role.
   * **Self-sign-up:** the page calls Cognito `SignUp` with the immutable custom attribute `custom:role`.
   * The **PreSignUp** Lambda trigger (`trialscout-signup-trigger`) validates the role and username (3–32 characters: letters, digits, `.`, `_`, `-`) and auto-confirms the user.
   * The **PostConfirmation** trigger adds the user to that group.
   * The access token then carries `cognito:groups`, which drives the agent's tool list and the Gateway RBAC interceptor.
   * Pool policy: minimum 6 characters, no complexity rules, MFA off, no e-mail verification. This is classroom convenience, not a production setting.
   * Accounts made through the hosted UI's own sign-up link get `reader`, because that page cannot set the role.
3. `POST /api/chat` goes CloudFront → **API Gateway REST**, which has a Cognito authorizer, throttling, response streaming, and a regional WAF that requires the secret `x-origin-verify` header only CloudFront sends. API Gateway calls the **chat proxy Lambda** (Node 22, response streaming).
4. The proxy forwards the **user's own JWT** to the **AgentCore Runtime** `trialscout_agent` (HTTP protocol). The runtime's JWT authorizer accepts only the SPA client.
5. The agent (Strands) runs these steps:
   * `ApplyGuardrail` on the raw input.
   * Load long-term preferences from **AgentCore Memory** into the system prompt.
   * Open an MCP session to **AgentCore Gateway** with the same user JWT.
   * List the tools, filtered by role.
   * Run the model/tool loop.
   * Wrap every tool result in `<untrusted_tool_data>`.
   * Stream SSE events (`meta`, `text`, `tool`, `blocked`, `error`, `done`).
6. The Gateway validates the JWT (third check) and calls the **RBAC interceptor Lambda**. The interceptor filters `tools/list` and denies a disallowed `tools/call` with JSON-RPC error -32003. The Gateway then gets an OAuth client-credentials token from **AgentCore Identity** and calls the target MCP runtime.
7. **MCP runtimes** `trialscout_study_mcp` (search_studies, get_site_performance, forecast_enrollment) and `trialscout_policy_mcp` (search_documents, check_compliance, summarize_amendment) accept only the Gateway's M2M client.
8. Short-term memory saves every turn as an event per (user, session). Long-term memory extracts preferences under `/users/{actorId}/preferences`.

**Roles:**
* `reader`: search_studies, get_site_performance, search_documents.
* `analyst`: all six tools.

The interceptor enforces this, and the agent mirrors it.

## 5. TrialScout Insights architecture (this app)

* **Static:** `insights-web/` (vanilla JS, no build step) sits in the private S3 bucket `trialscout-insights-site-<account>`. It is served by its own CloudFront distribution with its own WAF (`trialscout-insights-cloudfront`), ACM certificate and Route 53 alias `insights.awsteach.com`.
* **Dynamic:** all of it comes from two Lambda functions (Node.js 22, arm64). CloudFront reaches them through **Origin Access Control on Lambda Function URLs** (`AWS_IAM` auth), so the URLs cannot be called directly.
  * `trialscout-insights-api` (buffered JSON) serves `/api/overview`, `/api/inventory`, `/api/knowledge`, `/api/log-sources`, `/api/logs`, `/api/llm`, `/api/metrics`, `/api/source`, and `/api/health`.
  * `trialscout-insights-chat` (`RESPONSE_STREAM`) serves `/api/chat`, an SSE stream of `meta`, `thinking`, `text`, `tool`, `tool_result`, `done` and `error` events.
* **Auth:** sign-in uses the same Cognito pool through a separate app client, `trialscout-insights-spa`.
  * Because OAC re-signs the `Authorization` header with SigV4, the browser sends its access token in `X-Insights-Token`.
  * For POST bodies the browser also sends `x-amz-content-sha256`, which OAC requires for Lambda URL origins.
  * Each Lambda verifies the JWT itself: RS256 signature against the pool JWKS, issuer, `token_use=access`, `client_id`, and expiry.
* **Chatbot tools** (all read-only):
  * `get_inventory`: CloudFormation stacks and resources.
  * `query_logs`: allow-listed log groups only.
  * `get_llm_invocations`: the Bedrock invocation log, including prompts and reasoning.
  * `get_metrics`: a fixed CloudWatch metric catalog.
  * `list_source_files` / `read_source_file`: the code snapshot.
* **Grounding:** this file sits in the system prompt behind a prompt-cache checkpoint. The bot answers design questions from it, and calls tools for anything live.
* **Knowledge bucket:** the private, versioned bucket `trialscout-insights-knowledge-<account>` holds `projectknowledge.md` and `source/` (manifest plus files). Old versions expire after 30 days.

### Reasoning logging for every LLM prompt

The Insights stack enables **Amazon Bedrock model invocation logging** for the account in us-east-1, through an `AwsCustomResource` that calls `PutModelInvocationLoggingConfiguration`. Deleting the stack disables it again.

* **Destination:** the CloudWatch log group `/aws/bedrock/trialscout-model-invocations`, encrypted with the TrialScout CMK, with 14-day retention. Bodies over 100 KB spill to `s3://trialscout-invocation-logs-<account>/large/`.
* **Contents:** text request and response bodies only (embeddings, images and video are off). Every Converse/ConverseStream call is recorded: the system prompt, the messages, the tools offered, `additionalModelRequestFields` (the thinking config), `requestMetadata`, and the token counts. The output includes the **reasoning text** (adaptive thinking), the tool calls and the answer.
* **Who can see it:** every signed-in student sees **every** student's calls from both apps. Each call carries `requestMetadata.user` (the Cognito username), so the LLM reasoning tab and the chatbot's `get_llm_invocations` tool can filter by student.
* **Identifying the app:** the log's `identity.arn` gives the caller. Role `trialscout-agent-runtime` means the TrialScout agent; role `trialscout-insights-chat` means this chatbot. `requestMetadata.correlation_id` ties a call to a chat request.
* **What is not captured:** AgentCore Memory's own extraction calls run inside the service, so they are not logged in this account. Guardrail checks are not LLM prompts.
* **Why it is separate from the app logs:** the TrialScout services never log prompts or answers (privacy by design in `tslog.py`). The invocation log is the one controlled place where full prompts exist. It is KMS-encrypted, short-retention, readable only by allow-listed roles, and values are redacted again before display.

### How Insights avoids exposing secrets

* **IAM:**
  * The Insights Lambdas have read-only permissions on an allow-list.
  * An explicit **Deny** on `secretsmanager:GetSecretValue`, `ssm:GetParameter*` and `cognito-idp:DescribeUserPoolClient` covers the case where a broader policy is ever attached.
  * The Lambdas have no AgentCore, DynamoDB-write or S3-write permissions.
* **Redaction:** every value sent to the browser or the LLM goes through `redact()` (`lambdas/insights/lib.mjs`). It masks JWTs, AWS access key IDs, private keys, bearer tokens, `password`/`client_secret`/`x-origin-verify`/token fields, e-mail addresses, phone numbers and SSNs.
* **Stack outputs** whose key contains "secret" are dropped. The publish script refuses to upload source files that match credential patterns.
* **What does exist as secrets** (names only; values are never readable here):
  * `trialscout/origin-verify`: the CloudFront → API Gateway shared header.
  * The Cognito M2M client secret: copied straight into the AgentCore Identity token vault (`bedrock-agentcore-identity!default/oauth2/trialscout-gateway-to-mcp`) by a custom resource.

## 6. AgentCore components (one-paragraph explanations)

* **Runtime**: serverless, session-isolated microVM hosting for agents and MCP servers. Each session ID gets its own microVM (≥ 33-character session IDs; a new session costs about 7–9 s of cold start). This deployment has three runtimes, deployed as **code zips** (Python 3.12, linux/aarch64 wheels, `opentelemetry-instrument main.py` entry point) rather than containers. Inbound auth is a JWT authorizer per runtime.
* **Gateway**: one MCP endpoint that aggregates tools from several targets as `target___tool`. It validates the inbound JWT, runs a Lambda **interceptor** on requests and responses (used here for RBAC), and gets outbound credentials per target from Identity.
* **Identity**: inbound JWT authorizers, plus outbound **OAuth2 credential providers** whose client secrets live in a managed token vault. Here, the provider `trialscout-gateway-to-mcp` (CustomOauth2 against the Cognito discovery URL) lets the Gateway call the MCP runtimes with client-credentials tokens.
* **Memory**: `trialscout_memory` (CMK-encrypted, 30-day event expiry). Short-term memory stores the session's turn events (`AgentCoreMemorySessionManager`). The long-term **user preference** strategy writes to `/users/{actorId}/preferences`, which the agent retrieves with semantic search and adds to the system prompt.
* **Observability**: ADOT/OpenTelemetry in every runtime. APPLICATION_LOGS go to vended log groups and TRACES to X-Ray, with **Transaction Search** writing spans to the reserved `aws/spans` log group. View them in CloudWatch → GenAI Observability → Bedrock AgentCore, plus the `trialscout-ops` dashboard and 7 alarms.

## 7. Infrastructure as code and deployment

* **Tooling:** AWS CDK v2 in TypeScript (`aws-cdk-lib` 2.274, project-local CLI 2.1146), using L1 `Cfn*` constructs for AgentCore. It has its own bootstrap stack, `TrialScout-CDKToolkit` (qualifier `tscout`).
* **Stacks, in deploy order:**
  * `TrialScout-Foundation`: KMS, DynamoDB, docs bucket, Cognito, secrets, guardrail, SNS, budget.
  * `TrialScout-AgentCore`: 3 runtimes, Gateway + targets + interceptor, Identity provider, Memory, guardrail version, observability deliveries.
  * `TrialScout-Api`: REST API, chat proxy, regional WAF.
  * `TrialScout-Web`: CloudFront, WAF, ACM, the www alias, the SPA.
  * `TrialScout-Observability`: dashboard and alarms.
  * `TrialScout-Insights`: this app, its knowledge bucket and invocation logging.
* **Commands:**
  * `make deploy`: preflight (refuses root credentials, checks the hosted zone and model access), build zips, bootstrap, Foundation, seed, the other stacks, then publish this knowledge file.
  * `make publish-knowledge`: refresh this file only.
  * `make smoke` (TrialScout) / `make insights-smoke` (Insights): live tests.
  * `make ui-check` / `make insights-ui-check`: headless browser checks.
  * `make teardown` / `make teardown-all`: delete everything; the second also removes the bootstrap.
* **Region and DNS:** `us-east-1`. Hosted zone `awsteach.com` (pre-existing, not modified apart from the `www` and `insights` alias records and their ACM validation CNAMEs).

## 8. Security and operations summary

* **Encryption:**
  * One customer-managed KMS key (`alias/trialscout-data`, rotation on) for DynamoDB, the docs bucket, secrets, SNS, the log groups, the guardrail, Memory and the invocation log.
  * TLS everywhere.
  * The static site buckets use SSE-S3.
* **WAF:**
  * TrialScout CloudFront: 300 requests per 5 min per IP on `/api/*`, plus IP reputation, common and known-bad-inputs rules.
  * A regional WAF on API Gateway enforces the origin header.
  * The Insights CloudFront WAF uses the same rules, with the common rule set's body-size rule in count mode because chat posts carry history.
* **Throttling:**
  * TrialScout API Gateway: stage 10 rps / burst 20; chat 5 rps / burst 10.
  * The Insights Lambdas have a reserved concurrency of 10 each.
* **Logging:**
  * Structured JSON with a `correlation_id` everywhere.
  * TrialScout never logs prompts, answers or tool payloads.
  * Insights logs `llm_call` metadata only (token counts, cache hits, latency, tool names).
* **Alarms:** API 5xx, proxy errors and throttles, agent errors, chat latency p90, guardrail block spike, Gateway denial spike. They go to SNS `trialscout-alarms`.
* **Budget:** `trialscout-monthly`, $100, with alerts at 80% actual and 100% forecast.

## 9. Cost (estimate, us-east-1)

TrialScout costs about **$60/month** with light classroom use (about 500 chats) and about **$25/month** idle.
Insights adds roughly **$8–15/month** with use:

* The WAF web ACL costs about $9.
* The Insights chatbot uses Claude. The knowledge prompt is about 20–25k tokens, but cache reads cost about 10% of the input price, so each question costs roughly $0.02–0.08.
* Invocation-log ingestion is small.
* Lambda, CloudFront and S3 cost pennies.

## 10. Known limitations

* Synthetic data only. Forecasts use a simple mean ± 1.28 σ band. Compliance checks are deterministic field rules, not a legal review.
* Retrieval uses an in-memory index loaded into each microVM. That is fine for 34 chunks; a Bedrock Knowledge Base suits real corpora.
* Defense against injection through tool output is wrapping plus heuristics plus instructions, not a second guardrail pass.
* Sign-up is open to anyone who can reach the site. The guards are WAF rate limits, API throttles and the $100 budget alarm; there is no invite code.
* Insights shows the invocation log for the last 14 days only. The log covers every Bedrock caller in the account and region (in this demo account that is only TrialScout).
* The Insights chatbot holds only the conversation text between turns (the browser sends the history), not earlier tool results or reasoning.
* Spans can take 2–5 minutes to appear, and log events about 5–60 seconds.
